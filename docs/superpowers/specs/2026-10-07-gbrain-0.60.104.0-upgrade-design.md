# Upgrade the supported gbrain pin to v0.60.104.0

**Date:** 2026-10-07
**Status:** design, not started
**Pin today:** `0.50.5.0` (`.env.example`, `HANDOFF.md`, published `gbrain-base:0.50.5.0`)
**Target:** `0.60.104.0`, the latest non-draft GitHub release of `garrytan/gbrain` as of 2026-10-07T20:19:08Z
**Not the target:** `master` `VERSION` (what `check-update` reports), a moving tag, or `0.60.105.0` (named by the schema-pack Phase B spec; that tag does not exist)

## Decision

Move Mobrain's supported gbrain pin from `0.50.5.0` to `0.60.104.0` through the existing host lane (`scripts/upgrade.ts`). One image swap to that exact tag. Do not install the 104 intermediate tags as images. Do not fork gbrain. Do not run `gbrain upgrade` or `gbrain self-upgrade`.

This is a catch-up of the support policy's 30-day target. Tags from `0.51.0.0` (2026-09-22) through `0.59.20.0` (2026-09-29) are already past that target. The work is the playbooks, the contract suite, and the upgrade gate — not the downtime.

## Lane facts that this delta breaks

These are already true in the `v0.60.104.0` sources. They are not guesses waiting on the contract suite.

1. **Bun.** `skills/migrations/v0.60.27.0.md` says every `gbrain` command except `--version` exits on Bun older than 1.4.0. `docker/gbrain-base.Dockerfile` smoke-tests `--version` first, so a 1.3.13 image can look healthy and then refuse `serve`, `apply-migrations`, and `--tools-json`. The base image becomes `oven/bun:1.4.2` (exact tag; the migration names 1.4.2 as the runtime compiled binaries carry). `docker/agent-runner.Dockerfile` stays on `1.3.13`: that image has no gbrain binary, and this upgrade does not move `HARNESS_VERSION`.

2. **`apply-migrations --yes` installs autopilot.** Upstream help at the target says `--yes` and `--non-interactive` both authorize the Phase F autopilot install. The skip is `--no-autopilot-install` or `GBRAIN_NO_AUTOPILOT_INSTALL=1`. `scripts/upgrade.ts` currently calls `applyMigrations` with `{ yes: true, nonInteractive: true }` and no skip. That is forbidden here (`lint:forbidden`, "never run `gbrain autopilot --install` in a container"). The schema step passes `noAutopilotInstall: true`. Compose also sets `GBRAIN_NO_AUTOPILOT_INSTALL=1` on every gbrain service, same shape as `GBRAIN_SELF_UPGRADE_MODE=off`.

3. **The schema journal currently describes the old delta.** After a zero exit, `scripts/upgrade.ts` writes "no migrations were pending" and cites `migrate.ts` being byte-identical from `0.50.0.0` to `0.50.5.0`. That sentence is false for this jump (migration skills name schema versions through at least v212). The journal records the exit code and, once a contract test has named them, the `--json` fields. It never claims the 0.50 delta.

4. **Doctor parity does not fail on new checks.** `compareDoctor` fails the run only when a check that was `ok` before is not `ok` after, or `schema_version` is not `ok`. New checks are recorded and do not roll back. Do not weaken that function to make this jump pass. A regression is a stop.

5. **`config get` redacts.** Upstream INSTALL at the target says sensitive key names print `***`, and a `postgres://` value loses its userinfo, unless `--raw`. `readConfigValue` parses the first non-`[config]` line. A redacted `mcp.publish_skills` would make `skillsPublished()` return false. Probe before adding `--raw`. Do not add `--raw` to every get: that puts secrets in transcripts.

6. **Postgres stays pg16** unless the fixture's `schema_version` check is not `ok`. Upstream's own `docker-compose.test.yml` at the target is `pgvector/pgvector:pg16`.

## What the lane already does, so playbooks must not redo it

Image swap, quiesce, snapshot, `apply-migrations`, `post-upgrade`, service restart, and the doctor gate are the run's steps. A migration file that says "run `gbrain upgrade`" is not a step and is not executed. The quote goes in the spec's evidence. Restart, doctor, and a second `apply-migrations` are not steps either.

A numbered imperative becomes exactly one of:

- a `PlaybookStep` — a function of `UpgradeContext` that succeeds or throws, idempotent, no Docker, no SQL against gbrain tables, no operator judgement;
- a `ChecklistItemSpec` — judgement, paid work, a repair `--apply`, a grant change, an `embed --stale`, a `config set` that changes an operator default, or "tell the user";
- nothing extra, with the upstream sentence quoted, when the lane already does it.

Never both. Never "try, log, continue".

## Writers stay down when upstream says to ask first

Today a pending checklist keeps the banner up and blocks nothing else, and `run` resumes writers before a human can read it. Several target migration files say to tell the operator before the next sync or before a paid default starts (`v0.60.45.0` auto-chronicle, `v0.60.99.0` / `v0.60.102.0` fence rewrite, `v0.60.26.0` TypeSafe slots if a key is present, `v0.60.57.0` nightly relationship check). Resuming `gbrain-serve`, `gbrain-worker`, and `scheduler` at the end of `run` would start that work before the ack.

`ChecklistItemSpec` gains optional `blocksResume: true`. Default false, so the `0.50.2.0` item does not change.

When any opened item has `blocksResume`, `run` still resumes `gbrain-ops` and `control-plane` (the console has to show the checklist) and does **not** resume `agent-runner`, `scheduler`, `gbrain-worker`, or `gbrain-serve`. The journal's `gated_ok` event records `{ writers: 'held', reason: 'blocks_resume' }`. The run stays `gated_ok`. It is not `completed`, and `status` must not classify that hold as "roll back".

A new host command finishes it:

```bash
bun run scripts/upgrade.ts resume-writers --run <runId>
```

It reads the journal, refuses while any `blocksResume` item is still `pending`, applies a declined item's allowlisted opt-out through ops RPC, then resumes the four held services and enters `completed`. The control plane does not start containers. Decline without an opt-out does not count as settled for a `blocksResume` item: the writers stay down until the admin acknowledges (upstream default will run) or declines with the quoted opt-out.

No new `upgrade_runs.state` value. The CHECK list stays as it is. The hold is journal data on `gated_ok`, which `resumeFrom` already treats as post-swap; the status text is what changes.

The reader of each migration file confirms `blocksResume`. The files above are the ones the headers already require it for. PGLite-only notices (`v0.60.53.0` facts drain) are checklist text, not `blocksResume`, on this Postgres deployment.

Do not silently `config set` those defaults off. That is the same judgement, made by us instead of the admin.

## Contract surface

45 allowlisted operations in `src/contracts/registry.ts`. `docker/control-plane.Dockerfile` refuses to build without `contracts/v<pin>/operations.json`. Emit that file, and `capability.json`, for `0.60.104.0` before any control-plane build at the new pin.

Re-measure every operation against the new image. Known places the old comments are already false, to confirm rather than assume:

- `apply-migrations` now has `--json`, `--dry-run`, and `--no-autopilot-install`. `supportsJson: false` and the "exit codes are 0/1/2 and there is no --json" comment in `scripts/upgrade.ts` are the old pin.
- `page.delete --force` is already gated by `pageDeleteNeedsForce()` at `>= 0.51.0.0`. Callers must keep using that helper. Do not pass `--force` unconditionally in a way that breaks a rollback to `0.50.5.0`.
- Purge receipts already have both vocabularies in `src/contracts/receipts.ts`.
- `gbrain-base-v2` gains an `account` type at `v0.60.62.0`. Pack bytes are not identical to `0.50.5.0`. The `v0.50.2.0` playbook comment that says they are must not be copied forward.
- MCP search/query rows for remote callers are lean unless `mcp.result_rows` is `full` (`v0.60.44.0`). New stdio registrations default to the `starter` surface (`v0.60.61.0`). Diff the captured capability. Change a skill only where it names a removed field.
- `gbrain jobs supervisor stop --json` renames reason `timeout_40s` to `timeout` (`v0.60.74.0`). Quiesce uses `docker compose stop` and the supervisor audit log, not that reason string. Probe; do not retune grace periods unless the probe shows the drain proof broke.
- Pending CLI writes can exit 10 (`v0.60.36.0`). `okExitCodes` stays `[0]` unless a contract test shows an allowlisted op we depend on now exits 10 for success. Exit 10 is not success.
- OAuth access tokens are clamped, and already-issued access tokens shorten to 90 days (`v0.60.74.0`, migration v210). Checklist, not a new token-refresh feature.
- `serve --http` can stay up in status-only mode if the brain cannot open (`v0.60.61.0`). Health must not treat "HTTP listens" as "brain is up" if the probe shows that split. `/api/health` already has component states; extend it only if the probe shows a lie.

`schema_pack.source.<id>` readback is **not** this upgrade. `docs/superpowers/specs/2026-10-07-mobrain-core-and-life-schema-packs-design.md` Phase B wants `>= 0.60.105.0` and its own plan. Probe whether `schema active --source` works at `0.60.104.0`, record MEASURED or FALSIFIED, and leave the console copy that says there is no per-Space readback in place until that later plan.

## What a supported upgrade ships

`scripts/upgrade.ts` rebuilds `gbrain-base` and the control-plane image from the checkout it is run in. A `v1.0.0` host that checks out this tree and runs `--to 0.60.104.0` also ships everything on `main` since `v1.0.0` (zones, Google sign-in, schema packs, console). That is acceptable only as a new Mobrain release, chosen separately. This design does not tag, does not `docker push`, and does not backport the pin onto `v1.0.0`.

The supported pin in `.env.example`, `docker/control-plane.Dockerfile`'s default `ARG`, `README.md`, and `docs/support-policy.md` changes only after `playbooksFor('0.50.5.0', '0.60.104.0')` returns and a fixture run has completed or rolled back cleanly. Until then the declared pin stays `0.50.5.0`.

The fixture is not the shared dev stack. `scripts/upgrade.ts` always passes `--env-file .env` and `compose/docker-compose.yml`, and that file's project name defaults to `brainstand`. The run happens in a worktree whose `.env` is built from `.env.example` (no real `.env` secrets) and sets `COMPOSE_PROJECT_NAME=gbrain-upgrade-fixture`. Contract measurement uses `compose/docker-compose.slice0.yml` with `COMPOSE_PROJECT_NAME=brainstand-slice0-060`, not the fixture project and not the dev volumes.

## Out of scope

- Schema-pack Phase B, company packs, `mobrain-individual`.
- A Mobrain version tag, GHCR publish, or a gbrain-only backport branch.
- Harness pin, agent-runner Bun image, Postgres major version (unless the fixture falsifies pg16).
- Editing gbrain, reading its tables, or screen-scraping CLI prose.
- Silently disabling auto-chronicle, fence normalization, or TypeSafe slots.
- Iterating on this via GitHub Actions. One `stack.yml` contract dispatch after the local suite is green. No second dispatch to debug.

## Done

- `bun run scripts/upgrade.ts plan --to 0.60.104.0` exits 0 against a checkout whose pin is `0.50.5.0`.
- A fixture brain at `0.50.5.0` runs to `completed`, or to `gated_ok` with writers held and a printed `resume-writers` command, with `apply-migrations` not installing autopilot and `doctor` parity holding.
- `rollback --run <id>` restores the pin and the binary to `0.50.5.0`.
- The contract suite is green with `GBRAIN_VERSION=0.60.104.0`.
- `docs/support-policy.md` names `0.60.104.0` as the only supported gbrain.
